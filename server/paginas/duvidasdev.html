Visão geral

Sistema web de estoque e previsão de compras da GesToque. Não registra vendas: o consumo vem das saídas lançadas. Uma única aplicação serve a tela e a API, no mesmo endereço.

BancoPostgreSQL no Supabase (driver pg), schema gestoque. Sem banco configurado: PGlite (Postgres em arquivo).server/db.js, data/pglite

Dependências de produção: pg, @electric-sql/pglite, exceljs (planilhas) e qrcode (QR do autenticador). Criptografia, sessão e TOTP usam só o módulo crypto do Node.

Tipo de API

A API é REST com JSON sobre HTTPS. Não é SOAP (não há XML nem WSDL) e não é GraphQL. Cada recurso tem um caminho em /api/... e o verbo HTTP diz a ação.

VerboUso no sistema
GETConsultar (lista, detalhe, exportação). Nunca altera dados.
POSTCriar ou executar uma ação (lançar movimentação, importar, aprovar)
PUTGravar um valor inteiro (métricas, estimativa manual)
PATCHAlterar parte de um registro (item, usuário, preferências)
DELETEApagar (item, estimativa manual)
Formatos Pedido: Content-Type: application/json. Importação de planilha: o arquivo vai cru no corpo, com application/octet-stream (limite de 6 MB). Resposta: JSON (Cache-Control: no-store). Exportação: o arquivo (.xlsx ou .csv) com Content-Disposition: attachment. Filtros vão na query string (?item=12&tipo=saida). Ids vão no caminho (/api/itens/12).
StatusQuando
200Deu certo. Sem dados para devolver: {"ok": true}
400Dado inválido (a mensagem diz qual)
401Sem sessão, sessão vencida, sem token ou token errado. Também senha ou código errados.
403Perfil sem permissão, ou ação sem X-GT / de outra origem
404Rota ou registro não existe
409Conflito (SKU ou login repetido, solicitação já respondida)
413Arquivo maior que 6 MB
423Usuário bloqueado por erros no código (só admin libera)
429Espera após erros de senha ou de código

Todo erro volta como {"error": "mensagem em português"}, pronta para mostrar na tela.

Autenticação

O login tem duas etapas (senha + código TOTP). Depois dele, cada chamada à API leva duas credenciais: um cookie de sessão e um token de acesso no cabeçalho Authorization: Bearer. Não é JWT: os dois são tokens opacos (aleatórios, sem dados dentro) e quem decide se valem é o banco.

Cookie de sessãoToken de acesso (Bearer)
Nomegt_sessaocabeçalho Authorization: Bearer <token>
Formato32 bytes aleatórios (base64url)64 caracteres hex: sha256("api:" + cookie)
No bancosó o sha256 do valor (sessions.token_hash)nada: é recalculado a partir do cookie
Quem lêsó o navegador (HttpOnly: o JavaScript não lê)a tela, que guarda só na memória da página

Fimao sair, ao trocar a senha, 45 min sem uso (ou nunca, com "Manter ativo")junto com a sessão

Fluxo

  1. POST /api/entrar com usuário e senha. Senha certa: cria uma sessão provisória (10 min, mfa_ok = false) e devolve {"step": "codigo"} (ou "ativar" com o QR, no primeiro acesso).
  2. POST /api/entrar/codigo com o código de 6 dígitos. Código certo: apaga a sessão provisória, cria a definitiva com cookie novo (evita fixação de sessão), encerra outras sessões do mesmo usuário no mesmo navegador (cookie gt_aparelho) e devolve {"user": ..., "token": ...}.
  3. A tela guarda o token na memória e manda em toda chamada. Ao recarregar a página, GET /api/eu devolve o token de novo (só para quem tem o cookie).
  4. Cada uso empurra o fim da sessão (gravado no máximo 1 vez por minuto). POST /api/sair apaga a sessão.

Por que não JWT

JWT carrega os dados assinados e vale até expirar, mesmo que a pessoa saia ou seja desativada. Aqui a sessão mora no banco: sair, trocar a senha, desativar o usuário ou refazer o autenticador derruba o acesso na hora. O custo é uma consulta ao banco por chamada, pequeno para o tamanho do sistema.

Por que dois tokens

O cookie vai sozinho em qualquer pedido ao site. O token Bearer só existe para quem leu a resposta de /api/entrar/codigo ou /api/eu, e outro site não consegue ler essas respostas (política de mesma origem). Assim, um pedido montado em outro site, ou alguém que só tenha o cookie, não passa.

Código do autenticador (2FA)

TOTP padrão (RFC 6238): HMAC-SHA1, 6 dígitos, passos de 30 s, aceita o passo anterior e o seguinte. Um código só entra uma vez (last_totp_step, gravado de forma atômica). Erros: espera de 10 s, 100 s e 1000 s; o 4º erro seguido bloqueia até um admin liberar. A resposta de espera (401 do código ou 429) traz retry_in (segundos) e message_template (com {tempo}), e a tela conta o tempo ao vivo.

Perfis e níveis de acesso

Nível da rotaExige
abertoNada de login. Só as que precisam funcionar antes do login ou na página pública /version.
logadoSessão completa (senha + código) + token Bearer. Admin ou gestor.
adminO mesmo de "logado" e perfil admin. Gestor recebe 403.

Admin: tudo, incluindo usuários, métricas, excluir item, itens removidos e esta documentação. Gestor: a operação do dia a dia; pede usuários novos ao admin e vê só o próprio Perfil (nome, foto, usuário, perfil, data de cadastro), onde muda só o nome e a foto. A foto fica no Supabase Storage, bucket privado fotos-perfil (RLS + política restritiva fotos_perfil_fechado para anon/authenticated), sem link público: o servidor busca com a chave de serviço e entrega por GET /api/eu/foto?u=<id>&v=<versão>, só para quem está logado, com cache privado de 1 ano no navegador. No banco, só caminho, tipo e versão. O Registro da API grava inserir/trocar/remover, nunca a busca. Código: server/photos.js; banco local: data/fotos/.

A conferência é sempre no servidor. Esconder um botão na tela é só conforto: a API recusa mesmo que alguém chame direto.

Registro da API (/partner)

Toda chamada que muda algo, toda exportação e todo pedido que deu erro (inclusive acesso negado) vira uma linha em gestoque.api_logs. A tela /partner, só de admin, mostra a lista e, ao abrir uma linha, o JSON da solicitação e da resposta.

O que entraO que não entra
POST, PUT, PATCH, DELETE (criar, editar, excluir, importar, entrar, sair, aprovar...)Consultas GET que deram certo (listas, previsão, a própria tela de registro)
Exportações (GET .../exportar)O aviso de uso da tela (POST /api/eu/ativo, a cada minuto)
Qualquer pedido com status 400 ou mais (401, 403, 404, 409, 500...)
  • Quem: usuário da sessão com token válido. Login com senha errada aparece como "login tentado: usuário". Cookie válido sem token aparece como "... · sem token válido".
  • Dados exatos: pedido e resposta ficam em colunas json (não jsonb), que guardam os campos na ordem em que vieram.
  • Sigilo: campos password, current, next, code, secret, token, qr etc. viram *** antes de gravar, em qualquer nível do JSON.
  • Consulta SQL: o resultado não é guardado; fica só o SQL e um resumo (linhas, colunas, tempo). Uma rota pode pedir isso com ctx.logResponse.
  • Leveza: pedido ou resposta acima de 16 KB guarda só um trecho; arquivos enviados ou baixados guardam só nome e tamanho; registros com mais de 90 dias são apagados todo dia às 03:30 (Brasília) pelo pg_cron do Supabase (tarefa gestoque-limpar-api-logs), e aos domingos um VACUUM (gestoque-vacuum-api-logs) deixa o espaço pronto para os novos. O servidor tem uma limpeza de reserva a cada 6 h (banco local ou se o agendador falhar).
  • Sem atrasar o clique: o registro (e a renovação da sessão) roda junto com o pedido e termina depois da resposta (logs.afterReply). Na Vercel, waitUntil mantém a função viva até gravar; sem ele, espera antes de responder para não perder nada. Um erro ao gravar nunca derruba a chamada: só vai para o console.

Código: server/logs.js (gravação, GET /api/logs e GET /api/logs/:id) e o ponto de gravação em handleApi/handle (server/app.js). Tela: public/partner.html + js/partner.js.

Consulta SQL (só admin)

Tela "Consulta SQL" no menu: o admin escreve SQL (PostgreSQL) e lê qualquer dado de operação direto do banco. É só leitura, garantido em camadas, a principal no próprio banco.

CamadaComo
Papel no bancogestoque_leitura (sem login): SELECT nas tabelas de operação e no api_logs; na users só colunas sem segredo (sem pass_hash e totp_secret); sessions fechada. RLS com a política leitura_sql só para ele. Criado no SCHEMA; a conexão recebe SET no papel com INHERIT FALSE.
Transaçãoset transaction read only + role, search_path = gestoque e statement_timeout = 8s só dentro dela.
Texto da consultaComeça com SELECT, WITH, TABLE ou VALUES; sem ; no meio; sem funções que troquem de papel ou rodem outro SQL (set_config, query_to_xml, dblink, pg_sleep...). Envolvida em select * from (...) limit 1001, no protocolo estendido, que recusa vários comandos.
ResultadoAté 1000 linhas, colunas com o mesmo nome preservadas (rowMode: 'array'). O resultado é volátil: só vai para a tela. O Registro da API guarda quem, quando, o SQL enviado e um resumo (nº de linhas, nomes das colunas, tempo), nunca as linhas (ctx.logResponse).

Rotas: GET /api/sql/tabelas (tabelas e colunas visíveis) e POST /api/sql ({ sql }). Código: server/sql.js. Nomes sem aspas valem em maiúsculas ou minúsculas (Items = items); o preço do item é cost.

Testado em 2026-10-18 No Supabase de dev (Postgres 17, usuário sem superuser): papel criado, consulta com current_user = gestoque_leitura, senha e sessões recusadas, tempo limite cortando em 8 s. No banco local (PGlite) o tempo limite não age.

PostgreSQL no Supabase, tudo no schema gestoque. Sem DATABASE_URL válido o sistema usa o PGlite em data/pglite (um processo por vez).

Migração: editar o SCHEMA em server/db.js, sempre de forma idempotente (if not exists) e só acrescentando. Roda a cada início do servidor. Na Vercel use sempre o pooler (porta 6543): a conexão direta só tem IPv6.

Como fazer

Criar uma rota nova na API

Acrescente uma linha em routes (server/app.js): [método, /^\/api\/caminho$/, função, 'logado' ou 'admin', 'descrição']. Nunca 'aberto' sem motivo forte. A função recebe ctx (user, body, params, url, raw) e devolve um objeto (vira JSON) ou {file, name, type} para download. Erros: throw new HttpError(status, 'mensagem'). A rota aparece sozinha nesta lista; atualize também docs/API.md.

Criar uma página nova

Inclua /js/tema.js no <head> e /js/ambiente.js (tarja de teste) no fim do <body>. Se a página tiver endereço próprio, acrescente o apelido em PAGE_ALIASES e no vercel.json. Se for restrita, o conteúdo não pode ficar em public/: sirva por uma rota de API protegida, como esta.

Mudar o banco

Acrescente ao SCHEMA em server/db.js com create table if not exists / alter table ... add column if not exists. Nunca apague nem renomeie coluna em uso. Novas tabelas: ligue o RLS como as outras.

Lançar uma versão nova

Suba a versão em package.json e package-lock.json, acrescente o bloco no topo de server/novidades.json, atualize public/duvidas.html e esta documentação se algo técnico mudou. Commit no Dev; produção só com OK.

Manter o sistema rápido

Cada ida ao banco custa caro (~147 ms do computador até o Supabase de dev; ~70 ms do Preview). Consultas que não dependem uma da outra vão juntas em Promise.all; escrita frequente vira um comando SQL só (veja createMovement: CTE com for update, atômico sem begin/commit). Trabalho que não muda a resposta vai para log.side e termina depois dela. Para medir: servidor local com GT_ATRASO_BANCO=147, que simula a demora do Supabase.

Testar sem mexer no banco de dev

Suba um servidor separado com banco local: DATABASE_URL='' e PORT=3300. GT_ESPERAS_CODIGO=1,2,3 encurta as esperas do código. Para simular a produção (sem tarja): GT_AMBIENTE=producao.
